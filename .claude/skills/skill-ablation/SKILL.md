# Skill: Skill Ablation（skill の要否を確かめて削る）

skill を外した状態で同じ依頼を投げ、外しても出てくるものを skill から削る。
「足す」は簡単だが「削る」は根拠が要る。その根拠を、条件を揃えた実行と採点で作る。

対象の skill（とユーザーの狙い）が渡されていなければ、まずそれを確認する。

## 先にユーザーと合意すること

実行の前に、次の 5 つを書き出して承認をもらう。費用が掛かるので、ここを飛ばして実行しない。

1. **対象と「必ず出すもの」の一覧。** skill が定める出力のうち、生成物から観察できるもの（図、報告に書かれる値、コードの書き方）を 1 項目ずつ。観察できない指示（「慎重に」など）は採点できないので対象外と明記する
2. **ケース（依頼文）。** ユーザーが実際に打つ文面で、skill の名前・中身・採点項目には触れない。skill の中の分岐（手法・データの型）ごとに 1 件。試さない分岐は削らない、と先に決めておく
3. **条件。** 下の 3 つ（必要なら削ったあとの確認を 4 つ目に）
4. **回数と費用の見積もり。** 各 3 回が目安。条件数 × ケース数 × 回数 × 1 実行の費用（試運転で測る）。参考: データ分析の依頼 1 実行で 0.2〜2 ドル、3〜15 分（Claude Opus、effort medium）
5. **削る基準。** 下の「削る基準」を、結果を見る前に宣言する

| 条件 | 中身 | 何が分かるか |
|---|---|---|
| none | 対象の skill と、それに触れる記述（ルール文書の行、ほかの skill の節、説明文書）をすべて外す | skill が無くても出るもの |
| one-line | none に、ルール文書の 1 行（「〜したら、〜も出す」）だけを足す | 1 行で済むもの。skill に細かく書かなくてよい候補 |
| full | そのまま | 基準。ここで出ない項目は採点表か skill を疑う |

## 実験の道具

`scripts/ablate.py`（標準ライブラリだけ。Python 3.11 以上）と、設定の見本 `assets/ablation.example.toml` を使う。
uv を使うリポジトリなら `uv run python`、そうでなければ `python3` で実行する。

```bash
cp .claude/skills/skill-ablation/assets/ablation.example.toml ablation.toml   # 書き換える
python3 .claude/skills/skill-ablation/scripts/ablate.py plan                  # 操作と残った語の確認（claude は起動しない）
python3 .claude/skills/skill-ablation/scripts/ablate.py run --arm none --label exp1 --case c1 --repeat 1   # 試運転
python3 .claude/skills/skill-ablation/scripts/ablate.py run --arm none --label exp1 --resume             # 本番（条件ごと）
python3 .claude/skills/skill-ablation/scripts/ablate.py score outputs/ablation/exp1                      # 採点（API は呼ばない）
python3 .claude/skills/skill-ablation/scripts/ablate.py hits val-vif outputs/ablation/exp1               # 1 項目の根拠を目で見る
```

- sandbox はリポジトリの外（一時ディレクトリ）に、git 管理下のファイルだけをコピーして作る。リポジトリには書き込まない
- 結果は `outputs/ablation/<label>/<条件>/<ケース>/r<N>/`（`result.json`・`transcript.jsonl`・生成物 `files/`）。transcript に行データが残りうるので git に入れない
- 試運転と本番は、エージェントの Bash で `run_in_background` にし、終わるのを待つ。利用枠に当たったら、同じコマンドに `--resume` を付けて続きから

## 手順

1. **外す範囲を洗い出す。** skill のディレクトリ、ルール文書（`CLAUDE.md` / `AGENTS.md`）のルーティング表やハードルールの行、対象を前提にしたほかの skill の節、skill を説明した文書（README、docs、比較の記録）。設定の `remove` / `drop_lines` / `drop_sections` / `stub` / `include` / `exclude` に書く
2. **`plan` で残りを確かめる。** none と one-line の sandbox に `watch` の語が 0 件になるまで設定を直す
3. **試運転（1 ケース × 1 回）。** `result.json` の `permission_denials`（承認待ちで拒否されたツール）と、セットアップの失敗を潰す。拒否が出たら `allowed_tools` に足す
4. **本番。** 条件ごとに `run`。1 件ずつ順に（並列にすると利用枠を一気に使う）
5. **採点し、目で確かめる。** 条件の間で差が出たセルと、全回出たセルは、`hits` と生成物を読んで当たり外れを確かめる。言い回しの取りこぼし・誤検出を見つけたら採点表を直し、直した件数を記録する
6. **削る候補を決める。** 下の基準で
7. **削る。** 1 本の skill（reference）につき 1 コミットにする（戻すときに分かりやすい）
8. **削った版で確かめる。** full と同じケースを同じ回数。減った項目は戻して、もう一度確かめる
9. **記録を書く。** 下の「記録に書くこと」

## 削る基準

行（「必ず出す」の 1 項目）を削るのは、次の 3 つを全部満たすときだけ。

1. none でも one-line でも、全回出た（3 回ずつなら 6 回中 6 回）
2. その行の内容が、今回のケースですべて試せている（別の手法・条件分岐・別のデータ型を含む行は残す）
3. 出た時点で合格基準も満たしている。しきい値（「VIF < 10」）や違反時の対処（「5% 未満なら k を減らす」）を持つ行は、出たかどうかでは測れないので残す

**全回出たことは、削ってよい理由として十分ではない。** none は「skill が無い」状況で、「skill があって 1 行だけ無い」状況とは違う。
skill がある条件では、モデルは書いてある項目をやり、書いていない項目を省くことがある。
実例: MCMC のトレースプロットは none と one-line で 6 回とも描かれたが、行を削ると 3 回とも描かれなくなった。削ったあとの確認は省かない。

**コード例は、none との比較からは要否が分からない。** 削ってから確認で決める。その前に、コード例にしか書いていない指定（引数・既定値・手順）を表か本文へ移す。
移さずに消すと、出る項目は同じまま、やり方だけが skill なしのときに戻ることがある（例: 代入の方法が指定の方法から中央値に戻った）。採点の「出たか」では見えないので、確認で細部まで読む。

試していない分岐の行とコード例は残す。

## 採点表の書き方

- 1 項目 = 観察できる 1 つの出力。`figure` は「スクリプトに描画のコードがあり、画像ファイルがある」、`value` は「最終報告か保存した表に、その名前が出る」
- 否定の文（「確認していません」「was not checked」）は数えない。「このデータでは確かめられない」と書くこと自体が正解の項目だけ `allow_negation = true`
- 正規表現は広めに書く。言い換え（「当てはまりの検定」）、英語表記、自前実装（ライブラリ関数を使わず matplotlib で描いた図）、括弧から始まるタイトル（「(a) ...」。`[^)]` で切れる）
- 合格基準まで正規表現で測ろうとしない。しきい値を満たしたか、指定どおりの方法か、は目で見て記録に書く
- 1 回目の採点の後、full で出ていないセルがあれば、まず採点表を疑う

## はまりどころ

- **skill を説明した文書が skill の代わりになる。** README・docs・比較の記録・ほかの skill の参照が残ると、エージェントが読んで同じことをする。`stub`（中身を差し替え）か `exclude` で、どの条件でも同じにする
- **プロジェクトの外の同名 skill が見える。** `~/.claude/skills`、plugin、claude.ai のアカウントに登録した skill は、プロジェクトから消しても見える。`run` は見えていた skill 名を `watch` と照合して警告する。名前空間つき（`anthropic-skills:<名前>` など）なら `skill_overrides` で `off` にする。名前空間なしのもの（ユーザーレベル）は、ユーザーに一時的に退避してもらう
- **親セッションの環境変数。** Claude Code の中から起動すると、親の effort などが子に引き継がれる。スクリプトは既知の変数を外して起動する
- **headless では承認待ちのツールがすべて拒否される。** 拒否の回数を条件ごとに見て、偏っていないか確かめる。拒否のあとで方針を変える（スクリプトを書かずに手で答える）ことがある
- **エラー・タイムアウト・利用上限で終わった実行は「何も出なかった」に見える。** `score` はこれを数えず、件数だけ出す。自分のセッションも同じ利用枠を使う
- **費用は skill ありの方が高い**（例: 約 1.7 倍）。削っても下がらないことがある
- **結果を見てから基準を変えたら、変えたことと理由を記録に書く**

## 記録に書くこと

- 比べ方: モデル・effort・CLI のバージョン・日付、条件の中身、ケースのプロンプト、回数
- 結果: 項目 × 条件の「出た回数 / 実行回数」の表と合計、1 実行の費用と時間
- 削ったもの・残したもの（残した理由: 合格基準を持つ、試していない分岐を含む、など）と、行数の変化
- 削ったあとの確認の結果と、戻したもの
- 採点表を直した件数（取りこぼし・誤検出）
- 制約: ケースは skill の一部の分岐だけ、各 3 回、モデルは 1 つ、採点は正規表現
- 再現方法: 設定ファイルとコマンド、削る前のコミット
