# 診断 skill（*-diagnostics）に手法を追加する手順と雛形

`*-diagnostics` skill は 2 段構成です。

- **第 1 段（ルーター）**: `.claude/skills/<family>-diagnostics/SKILL.md`。常に読まれるのはここだけ（約 80 行）。ルーティング表・隣接 skill・「出力と報告」の共通書式を持つ
- **第 2 段（手法別 reference）**: 同じディレクトリの `references/<method>.md`。ルーターの表から選ばれたときだけ読まれる。「適用範囲 / ライブラリ / 必ず出す図 / 必ず出す値 / 落とし穴」の 5 節

## 手法を追加する手順

1. どのルーターの家族かを決める（統計的推論 / 予測モデリング / 因果推論 / 教師なし・EDA / シミュレーション・最適化）。どれにも入らなければ新しいルーターを作る（後述）
2. 下の雛形で `references/<method>.md` を書く。長さは 150 行程度までを目安にする（上限ではない。1 手法の診断に要ることだけを書く）。コード抜粋は主の手法の例と手法ごとの差分にブロックを分け、**実際に動かして確認してから**載せる。動くのが前提なので「動作確認済み」とは書かない
   - 1 つの reference に複数の手法を束ねるなら、図と値を「共通 + **使った手法の行だけ**」の表に分け、手法固有の行には区分列か `<手法>:` の前置き、条件付きの項目には「〜の場合のみ」を付ける。k-means を頼まれて階層クラスタリングの図が出る、のような過剰を防ぐため
   - 他の手法の部品として使われうる処理（診断図の PCA 射影、順列・ブートストラップの乱数、傾向スコアのロジスティック回帰など）があれば、「適用範囲」に本ファイルを適用しない使い方として書く
3. ルーター SKILL.md の「ルーティング表」に 1 行足す（手法名 / トリガー語彙（コードと日本語）/ 読むファイル）。ルーターの frontmatter `description` にも手法名とコード語彙を数語足す（1024 文字以内）。トリガー語彙には他の手法の中でも使う汎用 API（`np.random`・`default_rng`・`.sample(`・`groups=`・`minimize`・`scipy.stats` など）を入れない
4. 他ファイルへの参照（`docs/`、`src/`、他 skill のパス）を書かない。ディレクトリ単体で別リポジトリにコピーしても意味が通ること
5. `scripts/validate_agent_docs.py` の `DIAGNOSTICS_ROUTERS` に追加し、`README.md` の一覧表を更新する
6. 発火テストのケースを足す。`scripts/skill_eval/cases.yaml` の `variants` に新しい reference（表で分岐するなら表の 1 列目の各行）を宣言し、それを `covers` に持つケースを 1 件以上書く。`tests/test_skill_eval.py` が references の表と `variants` を照合するので、足し忘れると CI の pytest が落ちる。実際に発火するかは `uv run python scripts/run_skill_eval.py run --only <ケース id>` で確かめる（`claude -p` を起動するので費用がかかる。詳細は `scripts/skill_eval/README.md`）

## 新しいルーターを作る手順

1. `.claude/skills/<family>-diagnostics/SKILL.md` を既存ルーターをコピーして作る（見出しは「使い方 / ルーティング表 / 隣接する手法 / 出力と報告 / 全手法共通の落とし穴」で固定、100 行程度まで）。「使い方」の 1 番には、ユーザーが指示した手法の行だけを読むこと・他の手法の部品として使う処理は該当に数えないことを書く
2. `description` には (1) 家族の手法名を日英両方 (2) ライブラリ・クラス・関数名 (3) 診断に言及がなくても適用する明示 (4) 隣接ルーターの境界、の 4 点を入れる
3. 既存ルーターの「隣接する手法」表に新ルーターの行を足す
4. `scripts/validate_agent_docs.py` の `DIAGNOSTICS_ROUTERS` に追加する（Copilot・Codex は `.claude/skills/` をそのまま読むので、他陣営へのコピーやリンクは不要）
5. 配下の references について、上の「手法を追加する手順」の 6（発火テストのケース）を行う

## reference ファイルの雛形

````markdown
# <手法>の必須セット

短縮名: `<短縮名>`（図の保存先 `outputs/diagnostics/<YYYYMMDD-HHMM>_<短縮名>/`）。報告の書式と判定表はルーター SKILL.md の「出力と報告」に従う。

## 適用範囲

- 扱う: <この reference が対象とする手法を 1 行で>
- 扱わない: <隣接手法> → `references/<other>.md`（同じルーター）または `<router>-diagnostics`（`references/<x>.md`）
- （あれば）他の手法の部品として使うときは本ファイルを適用しない、という使い方

## ライブラリ

- 優先して使うもの（クラス・関数名まで書く）
- 未導入時の代替を 1 行（`uv add <package>` か、標準的な代替手段）

## 必ず出す図

共通（どの手法でも出す）:

- <図の名前> — <何が見えれば合格か>

**使った手法の行だけ**を追加する（手法が 1 つだけの reference なら表にせず箇条書きでよい）:

| 使った手法 | 出す図 | 合格の読み方 |
|---|---|---|
| <手法 A> | <図の名前> | <何が見えれば合格か> |

（1 手法 1 枚の複合図を基本。条件付きの図は「〜の場合のみ」と書く）

## 必ず出す値

| 区分 | 項目 | 合格基準 | 違反時の対処 |
|---|---|---|---|
| 共通 / <手法 A> | <統計量・件数・フラグ> | <数値の基準。流儀で割れるなら両方書く> | <次アクション。機械的に決められないものは「人間判断」と書く> |

取得例:

```python
# <主の手法で主要な値を 1 度に取る最小コード>
```

（手法ごとの差分は別ブロックにする）

## 落とし穴

- <5 項目程度。「やりがちな NG」と「なぜダメか」を 1 行で>
- <NG 例を 1 つ、コード 1〜2 行で>
````
